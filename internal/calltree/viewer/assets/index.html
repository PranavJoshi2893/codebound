Explore who calls whom, and how context moves through your code.

Start here: how to read this view
  1. Start at the root. Follow the call map left to right. Inside a function, read each panel downward, then follow its labeled continuation or exit.
  2. Click a function in the graph to select it. Choose Selected + neighbors to follow just its direct callers and calls, or search below.
  3. Start with Call flow. Choose Calls + context only when you need cancellation, deadlines, and values passed across calls.

Rows within one block preserve call evaluation order. Different blocks are alternative paths or continuations, not one top-to-bottom list. Function placement is not global execution order; this is not a runtime trace.

Arrow and context legend

Solid arrow: A → B means A may call B.

Forward calls leave the right side of a card and enter the next card’s header from the left. Calls back to another function use the opposite side. White breaks separate crossing routes; a crossing is not a junction.

↻ recursive call stays at its execution row and re-enters the same function’s entry, rather than drawing a tangled exterior loop. Its context bindings remain at that row.

Dotted arrow: a possible interface or function-value callback target. Dashed arrow: an indirect path through hidden calls, not a direct invocation. Possible HTTP dispatch: a recorded server-to-handler boundary, not route registration. Red arrow: a naming-based architecture warning, not proof of a bug.

Blue call arrow: context travels from the caller to the callee on this same arrow, not a separate path. Red warnings can override its color; the context label remains blue.

Boxes are functions. Shaded groups share a package and, when HTTP dispatch is present, a reachability phase: blue ENTRY / LIFECYCLE includes setup, route registration and server/shutdown logic; teal HTTP REQUEST is reached after dispatch; amber SHARED is reachable from both. These are possible paths, not a runtime schedule. Focused views retain the whole tree’s classification.

Tall terminal branches may occupy the next layout column to reduce empty space. Horizontal distance and vertical placement do not define execution order; block exits and call-site references do.

new C1 marks creation inside its function. C2 ← C1 marks a derived context in that function. Cancellation details remain in the explorer.

B0.2 identifies step 2 in block B0. True/false exits split and rejoin paths; loop marks a back edge. Only calls and channel actions are listed; ordinary value updates are omitted.

Alternative branches and independent closures share horizontal space. This does not mean they run concurrently. Long blocks use numbered continuation columns: read down one column, then follow continue → to the next step range. In multi-column cards, exterior call arrows name their exact step references instead of crossing neighbouring panels.

Register defer schedules work, not its immediate execution. The deferred stack runs last-registered-first at exit, including repeated registrations in loops. go launches concurrently; it does not wait before the next row. Closure bodies have separate entries and run only when invoked, not when declared.

ctx=C1 means this call passes context C1 into the callee’s ctx parameter.

C1 identifies a creation site, not a unique runtime object. I1 is an input created outside this tree. IDs are local to this analysis.

Possible / unknown: several origins may reach this point, or analysis could not trace an origin. This is uncertainty, not a confirmed bug.

One arrow summarizes calls between two functions. Combined context IDs are possible origins, not simultaneous values; partial means some variants lack binding evidence. An unlabeled call may still use context.

Observes Done: code receives from the cancellation channel; just getting Done() is weaker evidence. Neither proves the function stops.

Deferred: scheduled for when the function returns. Goroutine: launched concurrently. Interface: a possible implementation target.

Cancellation conditions are possibilities, not observed end times. Architecture warnings use naming heuristics, not a verified architecture policy.
